# 확정 설계 대비 구현 결정 점검

점검일: 2026-09-21. 이번 점검에서는 실행 코드·설정·운영 DB를 변경하지 않았다. 이 문서만 추가했다.

## 판단 기준

구현 전에 사용자가 수용한 원래 작업 폴더의 `design/continuous_briefing_design.md` v1.0을 기준으로, 구현 폴더의 코드와 대조했다. 구현 후 작성한 `continuous_briefing_implementation.md`의 선택사항을 사용자가 승인한 설계로 소급해 취급하지 않았다.

- 사용자는 초안 가정과 OOD를 확정했고, 구현 과정에서 드러난 중요한 미정 사항은 확인하도록 요청했다.
- 별도로 확인한 공개자료 범위는 **뉴스와 공식 공시 모두**다.
- 설계 1절·9절은 메서드, 자료형, DB 매핑, 공급자 어댑터, 타임아웃, 처리 용량을 구현 단계에 맡겼다. 모든 세부 수치를 다시 승인받아야 하는 것은 아니다.
- 분석 근거를 어디까지 읽는지, 언제 브리핑을 받을 수 있는지 같은 사용자 동작의 제약은 위 기술 세부사항과 구분해야 한다.

## 3. 정책 선택이 아니라 설계 대비 미완성인 부분

### A. 공개자료가 많을 때 요약·축소 없이 실패

- 설계 6.3절·7절: 중복 제거, 새 자료 우선, 원자료와 연결한 요약을 적용한다. 필수 차트·비교 맥락조차 담을 수 없을 때 실패한다.
- 구현: 건수 제한을 적용한 후에도 전체 입력이 600KB보다 크면 바로 실패한다. 용량에 맞춘 공개자료 요약·추가 축소 단계가 없다.
- 영향: 대상·차트가 작아도 뉴스가 많은 날 전체 브리핑이 실패할 수 있다.
- 근거: `app/application/briefing_analysis.py:21`.
- 오프라인 재현: 6종목 × 뉴스 10건 × 5,000자, 맥락 256바이트 / 자료 약 913KB에서 모델 호출 0회, 즉시 실패를 확인했다. 각 종목의 공개자료 개수는 현재 상한 이내였다.

### B. 정상 공시 0건과 부분 수집을 충분히 구분하지 않음

- 설계 FR-C05: 정상 0건, 실패, 지연, 자료 부족을 구분한다.
- 구현: SEC 수집기는 정상 응답에 공시가 전혀 없어도 `limited=True`를 반환해 상태가 `partial`이 된다. DART도 정상 목록에서 0건인 경로는 같은 문제 가능성이 있으며, DART 상태 013 경로만 명시적으로 `empty` 처리한다.
- 영향: 실제 0건을 조회한 경우에도 사용자는 ‘일부 자료’로만 보게 된다. 범위의 완전성 한계와 조회 건수를 분리해 보여줘야 한다.
- 근거: `app/integrations/briefing_sources.py:275`, `_fetch`의 상태 구성.
- 오프라인 재현: 모의 SEC 정상 응답의 `accessionNumber=[]` → 저장 후보 0건, 상태 `partial` 확인.

### C. 직전 비교 기준과 과거 근거의 화면 제공이 부족

- 설계 FR-C03·UC-C03: 실제 비교 날짜·종류·자료 기준과 당시 근거를 확인할 수 있어야 한다.
- 구현: 비교 문장에 날짜를 넣고 `previous_id`를 보존하지만, 화면은 이전 브리핑의 장전/장후 종류·기준 시각·이전 결론을 고정된 항목으로 표시하지 않으며 이전 브리핑으로 이동하는 기능도 없다. 모델이 설명에 써 줄 가능성에 의존한다.
- 추가로 전체 입력 중 **모델이 인용한** 공개자료만 화면에 보여준다. 인용하지 않은 저장 자료, 수집 시각, 제외 사유는 충분히 노출하지 않고 제외 건수만 보여준다. API의 저장 정보보다 화면에서 확인할 수 있는 범위가 좁다.
- 근거: `app/repositories/briefings.py:139`, `app/application/briefing_analysis.py:51`, `desktop-demo/src/components/briefings/briefing-panel.js:34`.

### D. 지침 파일 누락·손상의 상시 알림 부족

- 설계 7절: 마지막 유효 판본을 유지하면서 문제를 알린다.
- 구현: 실행 중에는 저장된 활성 판본만 조회한다. 누락·손상은 운영자가 CLI `status`나 미리보기를 실행해야 알 수 있다.
- 영향: 과거 판본으로 안전하게 계속 실행되지만, 파일 문제를 자동으로 안내하는 부분은 부족하다.
- 근거: `app/application/briefing_prompts.py:26`, `app/cli/briefing_prompt.py`의 `status` 처리.

### E. 새 공개자료 구분을 모델에 맡김

- 설계 3절: 직전 브리핑의 자료 기준 이후 공개된 자료를 새 근거로 구분한다.
- 구현: 공개 시각과 이전 맥락을 모델에 보내지만, 수집 단계에서 새 자료 여부를 명시적으로 분류하거나 화면에 고정 표시하지 않는다.
- 모델이 문장으로 구분할 수는 있으나 일관된 구분을 시스템이 보장하지 않는다. 이는 A·B처럼 오류를 재현한 항목과 달리, 계약 충족 방식이 약한 부분이다.

## 4. 이전 설계와 최신 설계 사이에 범위를 더 명확히 남길 부분

이전 `investment_briefing_revised_design.md`에는 예정 이벤트·지수·섹터·금리·환율 맥락(FR-B05)과 판단 변화·신뢰도별 정렬(FR-B12)이 있다. 현재 구현은 차트·뉴스·공시에 집중하고, 종목은 관심종목 순서로 반환한다. 이벤트/시장 맥락 전용 수집과 중요도 정렬은 없다.

최신 v1.0은 기존 문서를 참고 자료로 두고 자기 UC/FR과 변경표를 우선하므로, 이를 곧바로 최신 확정 요구사항 위반이라고 단정하지 않는다. 다만 이 기능들을 이번 구현에서 제외한다는 범위 표기가 충분하지 않았다. 이전 설계 전체까지 구현됐다고 해석하면 실제 구현과 차이가 난다.

## 5. 실행 준비에서 선택한 사항과 후속 승인

- 기존 수정 파일을 보존하려고 별도 worktree에서 작업했다.
- 앱 실행에는 별도 로컬 DB를 사용했다. 원래 DB의 관심종목·이력은 옮기지 않았다. 실행에 필요한 기존 환경 설정을 로컬 `.env`에 복사하고, 빠져 있던 알림 토큰 암호화 키는 새 로컬 DB용으로 생성했다.
- Gemini로 지침과 가상 예제를 보내 최초 검증·적용한 것은 **사용자가 별도로 승인한 뒤** 수행했다. 사용자 투자자료를 이용한 실전 브리핑 검증이나 실제 카카오 발송으로 간주하지 않는다.
- 이전 구현 기록의 ‘운영 키를 복사하거나 실제 Gemini 분석을 실행하지 않았다’ 문장은 그 문서 작성 당시 기준이며, 이후 실행·승인 단계까지 반영하지 못했다. 현재는 실제 앱 실행·카카오 로그인·Gemini 예제 검증 및 지침 적용까지 확인한 상태다. 공식 공시 실연동과 카카오 메시지 발송까지 검증한 상태는 아니다.

## 점검 결론

‘확정 설계를 기준으로 구현했다’는 설명은 맞지만, ‘모든 동작을 사전에 확인했고 설계를 완전히 충족했다’고 볼 수는 없다. 정확한 제공 시간, 공시를 읽는 범위, 생성 실패·누락 회차 정책은 별도로 확인되지 않은 선택이었다. 용량·DB·소유권 처리는 위임된 기술 결정이며, A~D는 기존 설계에 맞춰 보완할 항목이다.

이번 점검의 재현은 가상 데이터와 모의 HTTP 응답만 사용했다. 외부 모델 호출, 카카오 발송, 실행 중인 앱의 데이터 수정은 하지 않았다. 실행 코드의 수정은 포함하지 않았다.
