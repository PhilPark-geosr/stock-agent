# TradingView Paper Trading 참고 분석

- 작성·공식 자료 확인일: 2026-10-19
- 상태: 참고 서비스 분석 초안. Stock Agent의 모의투자 요구사항·OOA·구현 설계 확정 문서가 아니다.
- 추적 이슈: [#44 직접 판단 연습을 위한 모의투자 설계](https://github.com/PhilPark-geosr/stock-agent/issues/44)
- 작업 브랜치: `codex/paper-trading-design`
- 출발점: 최신 `origin/main`의 `e8beb05`

## 1. 목적과 분석 범위

사용자가 실제 돈을 쓰지 않고 직접 매수·보유·매도 판단을 연습하려는 목적에서 TradingView Paper Trading을 참고한다. 기능을 그대로 복제하거나 TradingView의 시세·계좌·API를 연동하기로 결정한 것은 아니다.

이 문서는 공식 도움말로 확인한 기능, 그 기능에서 얻은 설계 시사점, 우리 프로젝트의 미결정 정책을 구분한다. 실제 계정으로 주문·체결·Android 동작을 검증하지 않았으며, 내부 구현과 상세 체결 알고리즘은 분석 범위에 포함하지 않는다.

## 2. 우리 프로젝트에서 확인된 의도와 기존 합의

### 이번 논의에서 확인된 사용자 의도

- 사용자가 직접 모의 매매를 하면서 자신의 판단을 연습하고 싶다.
- TradingView Paper Trading을 참고하여 설계를 단계적으로 작성한다.

2026-10-19 요구사항 논의에서 초기 연습 방식은 현재 시장을 따라가며 실제 시간이 흐르는 동안 사용자가 직접 판단하는 방향으로 합의했다. 현재 목적·범위·위험은 [Inception](paper_trading_requirements.md), 합의된 상세 동작과 미결정 정책은 [Elaboration 준비 자료](paper_trading_elaboration_notes.md)에 기록한다. 아래 참고 분석에서 제안으로 기록한 항목의 현재 합의 상태도 두 문서를 기준으로 확인한다. 초기 주문·체결 범위는 아직 확정하지 않았으며, 자동매매를 이번 기능의 전제로 두지 않는다.

### 기존 합의와의 관계

개인 PC 분석 서버와 Android 모바일 이용, 연결 불가 시 이미 받은 결과 조회만 허용하고 새 분석·설정 변경 및 오프라인 요청의 자동 재실행을 허용하지 않는 방향은 유지한다. 다만 이 합의만으로 미체결 가상 주문의 처리나 모의투자 잔고의 오프라인 보관 정책까지 결정되지는 않는다.

기존 배포 논의는 [이슈 #42](https://github.com/PhilPark-geosr/stock-agent/issues/42)와 [당시 요구사항 문서](https://github.com/PhilPark-geosr/stock-agent/blob/3ef574482c80108feb57cee8e3603d0ddffe49f7/design/personal_pc_mobile_requirements.md)를 참고한다. 해당 문서는 이번 브랜치의 출발점인 main에 포함되어 있지 않으므로 이전 브랜치의 변경을 함께 가져오지 않는다.

기존 [CONTEXT.md](../CONTEXT.md)의 종목 분석은 모든 사용자에게 공통인 결과다. 이번 분석은 그 정의나 개인 실행 결과의 소유·공유 범위를 변경하지 않는다.

## 3. 참고 서비스의 목적과 시스템 경계

TradingView는 Paper Trading을 가상 자금으로 시장 상황에 따라 매매를 연습하는 기능으로 설명한다. 차트·분석 도구와 주문 및 보유 상태 확인을 연결한다. 주식 외에도 여러 자산군을 다루지만, 그 지원 범위를 우리 프로젝트의 요구사항으로 가져오지는 않는다. [S1]

이 문서에서 관찰하는 대상은 TradingView의 모의투자 서비스다. 사용자가 매매 판단의 주체이며, 시장 시세는 외부 입력이다. 실제 증권사 계좌 연결 거래와 TradingView 자체 Paper Trading은 구분한다. 내부 저장소나 처리기는 외부 액터로 가정하지 않는다.

## 4. 공식 문서로 확인한 기능

### 4.1 주문과 체결

주문 화면에서는 방향·수량·주문 방식을 지정한다. 시장가는 이용 가능한 시장 가격으로 체결되므로 기대 가격과 다를 수 있다. 지정가는 지정 조건과 유동성 등에 따라 미체결될 수 있고, 스톱 주문은 조건 도달 후 시장가 주문으로 전환된다. 주문 유효기간과 이익 실현·손실 제한 조건도 다룬다. [S3]

따라서 화면에서 매수를 요청한 사실과 실제로 가상 보유가 생긴 사실을 구분해야 한다. 공식 안내의 기능 설명만으로 부분 체결, 유동성 재현과 모든 예외의 세부 규칙을 확정할 수는 없다.

### 4.2 매수 기준 가격과 평가 기준 가격

공식 손익 안내는 대부분의 경우 매수에 Ask, 매도에 Bid를 사용하며 차트의 마지막 가격과 구분한다고 설명한다. 매수한 보유분의 평가손익은 청산 시 받을 수 있는 Bid와 평균 체결가의 차이에 수량을 곱해 계산한다. [S4]

따라서 “차트에서 확인한 현재가로 무조건 매수된다”는 설명은 정확하지 않다. 차트 가격, 주문 시 기대 가격, 실제 체결 가격, 현재 평가 가격은 서로 다를 수 있다. 우리 프로젝트가 단일 시세로 단순화하려면 그 한계를 별도 정책으로 명시해야 한다.

### 4.3 언제 결과를 확인하는가

계좌 화면은 열려 있는 보유분의 평가손익과 닫힌 거래의 실현손익을 구분한다. 보유 중에도 평가 결과를 확인하고, 청산한 거래는 계좌 이력에서 확인하는 구조다. 결과 확인을 위해 반드시 일주일이나 한 달을 기다리는 방식은 아니다. [S2]

Paper Trading은 현재 시장에서 연습하는 기능이므로 미래 시장을 빨리 진행시키지 않는다. 오늘 매수한 뒤 일주일 후의 상태를 보려면 실제 시간이 흘러야 한다. 과거를 재생하며 연습하는 기능은 별도 Replay Trading이다. [S1, S5]

### 4.4 계좌와 이력의 구성

| 구분 | 공식 안내에서 확인한 역할 |
| --- | --- |
| 계좌 요약 | 계좌 잔액·평가액, 실현·평가손익, 사용 가능한 자금과 증거금 관련 정보 |
| Positions | 현재 보유 상태 |
| Orders | 주문 상태 |
| History | 체결·거절·취소 등 주문 이력 |
| Account history | 종료한 보유분의 진입·청산 가격과 실현손익 |
| Trading journal | 주문과 시각에 관한 텍스트 기록 |

출처: [S2]. 이는 참고 서비스의 정보 구성이며 우리 프로젝트의 화면·클래스·저장 구조를 뜻하지 않는다. 특히 Trading journal을 사용자가 매수 이유와 회고를 직접 작성하는 투자 일지로 단정하지 않는다.

### 4.5 계좌 재설정과 비용

공식 안내는 서로 다른 통화의 계좌 생성과 계좌 초기화를 설명한다. 초기화하면 거래 이력·활성 주문·보유분이 삭제된다고 명시한다. [S6]

수수료를 모의 계산하는 기능도 존재한다. 공식 도움말은 선물·옵션의 계약 수 기준 수수료 설정을 설명한다. 이를 근거로 모든 시장의 세금·배당·환율·거래 비용이 실제와 동일하게 재현된다고 가정하지 않는다. [S7]

## 5. 시간과 결과를 이해하기 위한 예시

다음 값은 설명용이며 TradingView의 실제 거래 기록이 아니다. 수수료·세금·환율은 제외하고, 매수한 주식 10주의 평균 체결가를 50,000원으로 가정한다.

| 시점 | 사용자 행동·시장 상태 | 관찰 결과 |
| --- | --- | --- |
| 월요일 | 10주 매수 체결 | 평균 체결가 50,000원, 10주 보유 |
| 화요일 | 평가 기준 Bid가 52,000원 | 평가이익 20,000원. 아직 확정되지 않음 |
| 금요일 매도 전 | 평가 기준 Bid가 49,000원 | 평가손실 10,000원 |
| 금요일 매도 체결 | 10주를 49,000원에 전량 매도 | 실현손실 10,000원, 보유 수량 0주 |

관찰 결과를 묶으면 다음과 같다. 아래는 이용 흐름 설명이며 유스케이스·객체 시퀀스 다이어그램이 아니다.

```text
시장과 분석을 보고 판단
  → 주문 의사 전달
  → 체결 여부 확인
  → 보유 중 평가손익 관찰
  → 계속 보유하거나 매도 판단
  → 매도 체결 후 실현손익과 거래 이력 확인
```

## 6. 인접 기능과의 구분

| 기능 | 진행 방식 | 구분할 점 |
| --- | --- | --- |
| Paper Trading | 현재 시장 상황에서 가상 매매 | 직접 판단하고 보유 상태를 지속 관찰하는 참고 대상 [S1] |
| Replay Trading | 과거 시점에서 시작해 차트를 재생하며 가상 매매 | Paper Trading과 별도 모드이며 세션 결과와 보고서를 제공 [S5] |
| 전략 백테스팅 | 정해진 전략을 과거 데이터에 적용해 성과 평가 | 수동 판단 연습과 목적·입력이 다름 [S8] |
| The Leap | 대회 기간에 가상 매매 성과 경쟁 | 순위·대회 규칙이 추가되며 개인 연습의 필수 조건은 아님 [S8] |

이전에 대화에서 보여준 ‘다음 시점’ 데모는 만든 가격을 순서대로 진행한 개념 설명이다. 실제 시세나 TradingView의 체결 방식을 검증한 결과가 아니다.

## 7. 우리 프로젝트에 대한 해석과 제안

아래는 참고 서비스 분석에서 도출한 제안이며 채택된 기능 요구사항이 아니다.

| 관찰 | 제안 | 남는 판단 |
| --- | --- | --- |
| 주문·체결·보유 상태를 나눠 보여줌 | 매수 요청만으로 체결됐다고 표시하지 않기 | 초기 버전에 미체결 주문을 포함할지 |
| 보유 중 손익과 종료 거래 손익을 구분함 | 평가손익과 실현손익을 구분해서 설명하기 | 평가 가격·갱신 주기·비용 반영 기준 |
| 마지막 가격과 체결·평가 가격이 다를 수 있음 | 가격 기준과 시각을 명시하기 | 호가 확보 가능성, 단일 시세로 단순화할지 |
| 과거 재생은 별도 기능임 | 현재 시장 연습과 과거 재생 범위를 분리해 논의하기 | 초기 연습 방식을 무엇으로 할지 |
| 기존 분석 조회와 모의 매매를 연결할 수 있음 | 판단에 참고한 분석·이유와 이후 회고 연결 검토 | 기록을 필수로 할지, 분석과 연결할 범위 |
| 초기화는 과거 이력을 삭제할 수 있음 | 다시 연습하기와 기록 보존을 함께 논의하기 | 초기 자금·계좌 수·초기화·이력 보존 정책 |

핵심은 판단이 가격 변화 속에서 어떤 결과로 이어졌는지 이해하게 하는 것이다. 수익률만으로 판단의 근거가 옳았다고 결론내리지는 않는다. 매수 이유와 되돌아볼 시점 기록은 이 목적에 도움이 될 수 있지만 TradingView 기능을 확인한 사실과 구분한다.

## 8. 기술적 확인이 필요한 사항과 미결정 정책

모의 잔고·매매·손익 계산은 AI 호출과 독립적으로 구성할 수 있다는 것이 기술적 검토 방향이다. 그러나 현재 시세 기반 연습의 가능 범위를 정하려면 먼저 다음을 확인해야 한다.

- 대상 시장·종목의 가격 또는 Bid/Ask 확보 가능성, 지연·갱신 주기, 비용과 이용 조건
- 기존 로그인·관심 종목·공통 분석 조회의 재사용 범위와 새로 필요한 모의 주문·보유·이력 기능
- PC 중단 중 미체결 주문의 상태, 재연결 후 과거 체결을 소급할지, 처리 여부가 불명확한 요청의 중복 방지
- 모바일에서 보관할 잔고·거래 이력의 범위와 마지막 갱신 시각 표시

이번 문서는 위 항목의 코드·실기기 검증을 완료한 보고서가 아니다. 특히 PC가 꺼진 동안에도 TradingView처럼 계속 주문을 처리할 수 있다고 약속하지 않는다.

추가로 초기 자금, 시장가·지정가 지원, 주문 가능 시간, 부분 매도·추가 매수, 수수료·세금·배당·환율, 공매도·레버리지, 결과 공유 범위는 미결정이다. 우리 시스템에서 실제 거래 주문을 보내는 기능은 이번 설계 범위로 채택하지 않았다.

## 9. 후속 설계 순서

1. 이번 참고 분석을 바탕으로 연습 방식과 초기 범위를 한 항목씩 논의한다.
2. 시세 확보와 기존 기능 재사용 가능성을 먼저 조사하고 중요한 정책을 정한다.
3. 사용자 목표·시스템 경계와 외부에서 관찰 가능한 성공·예외를 OOA로 작성한다. 명세와 다이어그램은 분리한다.
4. 구체적인 동작 조건은 `FR-*` 요구사항으로 분리하고 유스케이스와 연결한다.
5. OOA 합의 후 도메인 모델 → 관계 중심 시퀀스 → 상세 클래스 순서로 진행한다. OOD 요소마다 근거 요구사항을 추적한다.

현재는 유스케이스 명세, 도메인 모델, 클래스·DB·API를 확정하지 않는다.
