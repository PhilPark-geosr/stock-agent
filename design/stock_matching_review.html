관심종목 등록·알림 설정·브리핑 실행은 결과를 받은 기능이 기존 규칙대로 처리합니다.

위 네 칸은 하나의 사용자 목표를 이루는 흐름입니다. 각각 별도 유스케이스가 아닙니다.

UC-S01 · 상장종목 지정

사용자 → 원하는 상장종목을 작업 대상으로 정하기

사용자가 알고 있는 정보를 제공하면 시스템이 후보를 구별해 보여줍니다. 사용자가 원하는 한 종목을 확인하고, 시스템이 현재 지정 가능한지 검증하여 결과를 알립니다.

일치 없음 · 여러 후보 · 지정 불가 · 정보 확인 불가 · 취소를 구분합니다. 성공 보장은 “사용자가 확인한 하나의 종목이 정해진다”입니다.

1. 도메인

입력에 대응하는 후보와 사용자가 확정한 결과를 구분합니다. 좁은 화면에서는 그림을 좌우로 이동할 수 있습니다.

같은 이름·별칭의 후보를 하나로 합치지 않습니다. 보통주와 우선주를 구별하고 코드 재사용을 새 상품과 과거 상품의 동일성으로 오인하지 않습니다.

2. 관계 중심 시퀀스

오퍼레이션·매개변수·DB 저장 순서 없이 책임의 협력만 표시합니다.

확정된 종목의 후속 사용은 이 시퀀스 밖의 책임입니다.

3. 주변 연결과 상세 클래스 설계

기존 그림은 책임 이름만 연결해 상세 설계로 읽기에 부족했습니다. 주변 코드의 연결과 내부 클래스 구조를 분리했습니다. 아래는 구현 전 설계이며 현재 제품 코드에 이미 존재하는 클래스 목록이 아닙니다.

점선: 사용·생성 의존성 / 실선과 숫자: 값의 연관·다중성 / + 공개, − 내부. 상세 그림은 좌우로 이동할 수 있습니다. 각 클래스가 별도 파일이나 서버를 뜻하지 않습니다.

3-1. 주변 코드와의 연결

현재 목록에서 찾는 search-form / selectStock()과 전체 종목 검색은 별개 책임입니다. 호출 기능이 확정 결과의 검증된 조회값으로 기존 등록 API를 호출합니다. 종목 지정 서비스가 등록을 수행하지 않습니다.

3-2. 검색 화면의 상태와 서비스 의존성

정렬 후에도 pendingId가 같은 후보를 유지합니다. 검색 조건에서 제외되면 미확정 선택만 해제하고, 취소·실패는 confirmed를 바꾸지 않습니다. 늦게 도착한 이전 요청은 무시합니다.

3-3. 검색·정렬·확정 클래스

카탈로그는 일치 후보를 찾고 서비스는 표시 순서를 정합니다. 확정할 때 현재 종목을 다시 조회합니다. 후보와 확정 결과의 종목 정보는 불변 스냅샷입니다. 관련도 기본 제안과 이름·코드 정렬의 규칙은 상세 설계서 10절에 있습니다.

3-4. 기준정보·별칭 갱신 클래스

위와 동일한 카탈로그의 쓰기 계약입니다. 한 국가의 실패로 다른 국가의 유효 정보를 지우지 않습니다. 동일 별칭은 여러 종목에 대응할 수 있지만 별칭 레코드 하나의 대상은 한 종목입니다.

규칙 재검토 결과

사용자 목표 중심·Essential Style·Black box 유스케이스와 최초 관계 중심 시퀀스는 유지했습니다. 기존 상세 설계의 부족한 점은 주변 연결, 속성·메서드·다중성, 정렬 책임 추적이었습니다.

명세 표에 UC ID·이름을 명시하고, 정렬을 기능 요구사항에 통합했습니다. 11개 규칙의 이전 상태와 보완 근거는 상세 설계서 9절에 있습니다. 실제 공급자·갱신 지연 허용시간·저장 기술은 확인 완료로 표시하지 않았습니다.
